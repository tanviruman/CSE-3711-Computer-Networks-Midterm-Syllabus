1Encapsulation — Core Concepts

Why Layering? Slide 1-46 to 1-50

Networks are complex (hosts, routers, links, applications, protocols, hardware). Layering gives an explicit structure so each layer implements a service using only the layer below it. Benefits: modularity, easier troubleshooting, and functionality reuse — a change inside one layer (e.g. gate procedure at an airport) is transparent to the rest of the system.

The Encapsulation Process Slide 1-51 to 1-56

Each layer takes the unit handed down from the layer above and wraps it with its own header (and sometimes trailer) to build its own protocol data unit (PDU):

Application → M (message) Transport → Ht | M (segment) Network → Hn | Ht | M (datagram/packet) Data Link → Hl | Hn | Ht | M | (Dt) (frame) Physical → raw bit stream

Your slides call this the Matryoshka / stacking-doll analogy 🪆 — each doll (layer) sits inside a bigger one, and nothing is thrown away as you go down the stack. De-encapsulation at the receiver is the exact reverse: each layer strips its own header/trailer and hands the payload up.

In the TCP/IP model (what your midterms actually give you numbers for), Presentation+Session collapse into Application, and Physical merges into "Network Access": so you only ever add 3 headers — Transport (TCP/UDP), Network (IP), Data Link — plus 1 trailer (Data Link only).

Which Device Processes Which Layer? Frequently tested — Summer'25 Q1a, Workbook KT3

DeviceLayers it processesWhy
Host (end system)All 5 layers (App → Physical)Both source & destination of the actual communication — needs to build/read every header.
RouterPhysical, Data Link, NetworkMust read the IP header to decide the outbound link ("routes packets"). De-encapsulates up to Layer 3 only, then re-encapsulates with a new Layer-2 header for the next hop.
Switch / BridgePhysical, Data Link onlyForwards based on MAC address; never looks inside the IP packet. It does not rewrite source/destination MAC — it's transparent.
💡 Direct answer for "which protocols run at intermediate nodes?"
Given {IP, UDP, Ethernet, SMTP, TCP, HTTP} → only IP and Ethernet run at intermediate nodes (routers process IP+Ethernet; switches process Ethernet only). TCP, UDP, SMTP, HTTP are end-to-end protocols — they exist only at the two communicating hosts, never at a router or switch in between.

1.2Formula Toolkit

Max payload per frame (MSS)
If frame size given excludes DL header/trailer → that number = Max IP packet size
MSS (max TCP data) = Max IP packet size − IP header − TCP header
Max payload per frame — alternate wording
If frame size given includes DL header/trailer →
MSS = Frame size − DL header − DL trailer − IP header − TCP header
Number of TCP segments needed
segments = ⌈ total application data ÷ MSS ⌉  (always round up)
last segment's data = total data − (segments−1) × MSS
Overhead % (per full-size segment)
overhead bytes = DL header + DL trailer + IP header + TCP header
overhead % = overhead bytes ÷ (overhead bytes + MSS) × 100
Latency for a segmented message over H hops (store-and-forward, pipelined)
T = (H + k − 1) × P
H = number of links (hops)  ·  k = number of PDUs  ·  P = size of one PDU (data + header)
⚠ Units assumption used throughout this guide
Unless a question explicitly says "1024", this guide uses the decimal networking convention consistently used in your slides/midterms: 1 KB = 1000 bytes, 1 Mbps = 10⁶ bps, 1 Gbps = 10⁹ bps. This matches the clean numbers your midterms are designed to produce (e.g. MSS = 1460B is the real-world Ethernet standard). Always double check with your instructor which convention is graded.

Overhead % for an L-byte messageWorkbook Ch.1 · Exercise 13
Given: L = 500 bytes message. TCP header = 20B. IP header = 20B. Data Link header+trailer = 18B combined. Find % of physical-layer bits that is actual message data.
Step 1 — Total frame size
Total = 500 + 20 + 20 + 18 = 558 bytes
Step 2 — Message %
500 ÷ 558 × 100 = 89.61%
Step 3 — Overhead % (its complement)
58 ÷ 558 × 100 = 10.39%
Message data = 89.61%  |  Overhead = 10.39%This is the exact pattern used in every "% overhead" midterm question — memorize this 3-step flow.
Understanding Packet Headers (H1 → Bridge → Router → H2)Workbook Ch.1 · Exercise 12
Given: H1 (port 8888) sends a TCP message to H2 (port 9999). Path: H1 —(X)— Bridge B —(Y)— Router R —(Z)— H2. Layers numbered 1=Physical…5=Application. List every point (X, Y, Z) and layer where each address appears.
Key rule
IP addresses & port numbers never change across the path (no NAT here) — they belong to Network (L3) and Transport (L4) headers, which only intermediate routers (not bridges) even look at, and neither device modifies them.
MAC addresses change every time the frame crosses a router (new L2 header per link) but stay the same across a bridge/switch (bridges are transparent — they forward the frame unmodified).
AddressWhere it's writtenReasoning
H2.ip{(X,L3), (Y,L3), (Z,L3)}Destination IP — set once by H1, unchanged end-to-end

Big picture: L3/L4 fields (IP, ports) are set once and never touched by intermediate nodes. L2 fields (MAC) are rewritten only by routers, never by bridges/switches.
Optimal PDU (packet) size for lowest latencyWorkbook Ch.1 · Exercise 14
Given: 150,000-byte message. Each PDU header = 200 bytes. Path has 2 packet-switching nodes → 3 links (H=3). Compare PDU data sizes: (i) 10,000B (ii) 2,500B (iii) 750B. Which gives lowest latency (in "bytes" of time, i.e. R normalized to 1 byte/unit)?
Formula
T = (H + k − 1) × P, where k = number of PDUs = 150,000 ÷ data-per-PDU, and P = data-per-PDU + 200 (header)
Scenariok (PDUs)P (bytes)T = (3+k−1)×P
(i) 10,000 B/PDU1510,20017 × 10,200 = 173,400
(ii) 2,500 B/PDU602,70062 × 2,700 = 167,400 ✅ lowest
(iii) 750 B/PDU200950202 × 950 = 191,900
Scenario (ii), 2,500 B/PDU, gives the shortest latency (167,400 byte-time-units). Why not the smallest PDU (iii)? Because although smaller PDUs pipeline faster per hop, you now need 200 PDUs → 200×200B = 40,000B of pure header overhead, which dominates. Why not the biggest PDU (i)? Because each store-and-forward hop now has to fully receive/re-transmit a much bigger chunk before forwarding, adding per-hop delay. The optimum is a trade-off in the middle.
TCP segments + overhead % for 2 MB of dataMidterm Spring 2026 · Q1(c)
Given: App layer = 2 Mbytes. TCP header 20B. IP header 20B. Data Link 14B header + 4B trailer. Frame size = 1500 bytes excluding header/trailer (i.e. this IS the max IP packet size / MTU).
Step 1 — Find MSS
Max IP packet = 1500B (given, MTU) → MSS = 1500 − 20(IP) − 20(TCP) = 1460 bytes (this is the real-world Ethernet MSS — a good sign your setup is right)
Step 2 — Segments needed
2,000,000 ÷ 1460 = 1369.86 → ⌈⌉ = 1370 segments
(1369 full segments of 1460B + 1 last segment of 2,000,000 − 1369×1460 = 1260B)
Step 3 — Overhead % (use a full-size segment)
Full frame = 14 + 20 + 20 + 1460 + 4 = 1518 bytes (again — the real Ethernet max frame size)
Overhead = 14+20+20+4 = 58B → 58 ÷ 1518 × 100 = 3.82%
1370 TCP segments required  |  Overhead ≈ 3.82% per full segment Bonus: if asked about the LAST (partial, 1260B) segment specifically, its overhead is higher: 58÷1318 = 4.40% — smaller payload ⇒ higher overhead ratio. Mention this if the question says "per segment" ambiguously.
4000-byte message, OSI model wording + frame-size changeMidterm Fall 2025 · Q1(d)
Given: 4000-byte application message. TCP 20B header, IP 20B header, DL 14B header + 4B trailer. Frame size = 1518 bytes, including header & trailer.
Part I — Encapsulation description (conceptual, always answer in words + a small diagram)
Application creates 4000B of data → Transport (TCP) adds 20B header → segment → Network (IP) adds 20B header → datagram/packet → Data Link adds 14B header + 4B trailer → frame → Physical layer transmits as raw bits. (Note the question says "OSI reference model" but only gives you Transport/Network/Data-Link headers — don't invent Presentation/Session headers that were never given numbers.)
Part II — TCP segments needed
MSS = 1518 − 14(DLH) − 4(DLT) − 20(IP) − 20(TCP) = 1460 bytes
Segments = ⌈4000 ÷ 1460⌉ = 3 segments
Data portions: 1460B, 1460B, 1080B (1460+1460+1080 = 4000 ✓)
Part III — Change when frame size reduced to 1200 bytes
New MSS = 1200 − 14 − 4 − 20 − 20 = 1142 bytes
New segments = ⌈4000 ÷ 1142⌉ = 4 segments (data: 1142, 1142, 1142, 574)
Overhead per segment is still 58B (14+20+20+4) regardless of size.
Old total overhead = 3 × 58 = 174B. New total overhead = 4 × 58 = 232B.
Total overhead increases by 58 bytes (174B → 232B, a 33.3% jump) Because the smaller frame forced one extra segment, and every extra segment costs one more full set of headers (58B). This is the same "smaller pieces ⇒ more overhead" idea as Exercise 14 above.

Given {IP, UDP, Ethernet, SMTP, TCP, HTTP}: only IP (at router T) and Ethernet (at both T and switch S) run at the intermediate nodes — because routers process up to Network layer and switches only process Data Link layer. 2 pieces of information needed: IP address + Port number (the socket tuple)

1.4Common Pitfalls — Encapsulation

⚠ Pitfall 1 — "Frame size" wording changes the formula
Always re-read whether the frame size given excludes header/trailer (→ it equals the max IP packet size directly) or includes them (→ subtract DL header+trailer first). Spring'26 Q1c uses "excluding"; Fall'25 Q1d uses "including" — mixing these up is the #1 way to lose the segment-count marks.
⚠ Pitfall 2 — Forgetting to round UP
Segments = ⌈data ÷ MSS⌉ — never round down or truncate. A remainder of even 1 byte still needs a full extra segment.
⚠ Pitfall 3 — Trailer is still overhead
Students often forget the 4-byte Data-Link trailer when computing "overhead". Overhead = ALL non-data bytes = every header + every trailer, not just headers, unless the question is extremely explicit that it wants headers only.
⚠ Pitfall 4 — MB/KB unit convention
"2 Mbytes" could mean 2×10⁶ or 2×2²⁰ bytes. This guide uses the decimal convention (matches the clean 1460/1518-byte real-world MSS numbers). State your assumption on the exam script if it isn't specified.
⚠ Pitfall 5 — Bridge/Switch does NOT rewrite MAC addresses
A very common mistake is assuming every intermediate device changes MAC addresses like a router does. Only routers rewrite Layer-2 addresses (because they generate a brand-new frame for the next link). Switches/bridges are transparent — the frame's MAC addresses pass through unchanged.

1.5Full-Marks Answer Checklist — Encapsulation Questions

  • Explicitly compute and label MSS (max TCP data per segment) before anything else.
  • Show the segment count formula with the ceiling symbol, then the arithmetic.
  • List the data portion of every segment (not just the count) if the question asks for "size of the data portion in each segment."
  • For overhead %, show overhead bytes and total frame bytes separately before dividing.
  • If frame size changes, reuse the same MSS formula — don't restart your logic; just show old vs new side-by-side.
  • For "which layer/device" questions, use the 3-row table (Host / Router / Switch) from Core Concepts above — examiners want the reasoning ("routers read L3 to route"), not just names.
  • Draw the small encapsulation staircase (M → Ht|M → Hn|Ht|M → Hl|Hn|Ht|M) whenever "illustrate/diagram" is asked — 1 minute of drawing for guaranteed marks.

2HTTP Math — Core Concepts

RTT and Response Time Slide 2-16, 2-17

RTT (Round-Trip Time): time for a small packet to travel from client to server and back. FTT (File Transmission Time): time to push all bits of one object onto the link = File Size ÷ Bandwidth.

Non-Persistent vs Persistent HTTP Slide 2-13, 2-17

TypeBehaviourCost per object
Non-persistentNew TCP connection for every single object; connection closed after each object1 RTT (TCP handshake) + 1 RTT (HTTP req/resp) + FTT = 2RTT + FTT
Persistent, no pipeliningOne TCP connection stays open; but client waits for each response before requesting the next object1 RTT (HTTP req/resp only, connection already open) + FTT = RTT + FTT, plus 1 RTT once for the initial handshake
Persistent, with pipeliningClient fires off all requests back-to-back without waiting for each responseOnly 1 RTT total is needed to request all the remaining objects — you then just pay their FTTs one after another

2.2Formula Toolkit — General n-Object Page

Let the page = 1 base HTML file + (n−1) embedded objects (all on the same server), n objects total.

① Non-persistent, no parallel connections
Total = n × (2RTT + FTT)   (if all objects are the same size)
or Σ (2RTT + FTTi) for each object individually if sizes differ
② Non-persistent, m parallel connections
Total = (2RTT + FTThtml)  +  ⌈(n−1)/m⌉ rounds × (2RTT + FTTobj)
③ Persistent, no pipelining
Total = 1RTT (handshake)  +  n × (1RTT + FTTi)   (request objects one at a time, sequentially)
④ Persistent, with pipelining
Total = 1RTT (handshake)  +  (1RTT + FTThtml)  +  (1RTT + Σ FTTobj)   (all remaining objects requested in one burst)
⚠ When the question just says "Persistent HTTP" with no mention of pipelining
Default to formula ③ (no pipelining) — that's the base behaviour of HTTP/1.1 persistent connections. Only use ④ if the question explicitly says "with pipelining."

50 Mbps link, RTT=100ms, HTML=7 Kbit + 5 images × 2.5 KbitWorkbook Ch.2 · Knowledge Test #2, Q5
Given: 6 objects total (1 html + 5 images). Link = 50 Mbps. RTT = 100 ms (includes propagation+processing+queueing). GET-message transmit time ≈ 0. Must include 1 RTT for TCP setup.
Step 0 — Compute FTTs first
FTThtml = 7,000 bits ÷ 50,000,000 bps = 0.14 ms
FTTimg = 2,500 bits ÷ 50,000,000 bps = 0.05 ms (each image)
(a) One non-persistent connection
(2RTT+FTThtml) + 5×(2RTT+FTTimg) = (200+0.14) + 5×(200+0.05)
= 200.14 + 1000.25 = 1200.39 ms ≈ 1.2 s
(b) Non-persistent, 2 parallel connections
HTML first (200.14ms), then 5 images in ⌈5/2⌉=3 rounds: 3×(200+0.05) = 600.15ms
Total = 200.14 + 600.15 = 800.29 ms ≈ 0.8 s
(c) Persistent, no pipelining
1RTT + (1RTT+FTThtml) + 5×(1RTT+FTTimg) = 100 + 100.14 + 5×100.05
= 100 + 100.14 + 500.25 = 700.39 ms ≈ 0.7 s
(d) Persistent, with pipelining
1RTT + (1RTT+FTThtml) + (1RTT + 5×FTTimg) = 100 + 100.14 + (100+0.25)
= 100 + 100.14 + 100.25 = 300.39 ms ≈ 0.3 s
(e) Are non-persistent connections ever preferable?
Yes — e.g. when objects are spread across different servers (persistent doesn't help since a new connection is needed per server anyway), or when a server needs to limit the number of simultaneously-open idle connections to serve many clients, or for simple stateless server designs.
a) 1200.39ms   b) 800.29ms   c) 700.39ms   d) 300.39ms Notice the clear ranking: non-persistent (worst) → parallel → persistent → persistent+pipelining (best). This ordering is itself a common short-answer question.
1 Gbps link: HTML + 2 CSS + 8 imagesMidterm Spring 2026 · Q2(b)
Given: 1 HTML (100KB) + 2 CSS (150KB each) + 8 images (2MB each) = 11 objects. Bandwidth = 1 Gbps. RTT (connection setup) = 0.2 ms — applied uniformly to every round trip.
Step 1 — FTT for each object type
FTThtml = 100,000×8 ÷ 10⁹ = 0.8 ms
FTTcss = 150,000×8 ÷ 10⁹ = 1.2 ms (×2 files)
FTTimg = 2,000,000×8 ÷ 10⁹ = 16 ms (×8 files)
Step 2 — Non-persistent HTTP
Total = (2×0.2+0.8) + 2×(2×0.2+1.2) + 8×(2×0.2+16)
= 1.2 + 2×1.6 + 8×16.4 = 1.2 + 3.2 + 131.2 = 135.6 ms
Step 3 — Persistent HTTP (no pipelining)
Total = 1×0.2(handshake) + (0.2+0.8) + 2×(0.2+1.2) + 8×(0.2+16)
= 0.2 + 1.0 + 2.8 + 129.6 = 133.6 ms
Non-persistent = 135.6 ms  |  Persistent = 133.6 ms Notice the gap is small (only 2ms) — because with a 1Gbps link the images' FTT (16ms each) totally dominates over the tiny RTT savings (0.2ms each). This is a great point to mention for "why is persistent HTTP not always dramatically faster" style follow-ups.
8 small objects, RTT=0.8s, 500 Kbps throughputMidterm Fall 2025 · Q2(b)
Given: Base HTML + 8 referenced objects = 9 objects total, each 100 Kbytes. RTT = 0.8 s. Throughput = 500 Kbps.
Step 1 — FTT per object
FTT = 100,000×8 bits ÷ 500,000 bps = 800,000 ÷ 500,000 = 1.6 s
Step 2 — Non-persistent HTTP
9 × (2RTT + FTT) = 9 × (1.6+1.6) = 9 × 3.2 = 28.8 s
Step 3 — Persistent HTTP (no pipelining)
1RTT + 9×(RTT+FTT) = 0.8 + 9×(0.8+1.6) = 0.8 + 9×2.4 = 0.8+21.6 = 22.4 s
Non-persistent = 28.8 s  |  Persistent = 22.4 s Bonus (only if "pipelining" is explicitly asked): Persistent+pipelining = RTT + (RTT+FTT) + (RTT+8×FTT) = 0.8+2.4+13.6 = 16.8 s.
Symbolic form: base page + 4 images (in terms of T1, T2, T3)Midterm Summer 2025 · Q3(a)
Given: T1 = time to establish a TCP connection. T2 = time to retrieve the base page. T3 = time to retrieve each image. 4 embedded images. Ignore connection-close time and GET-packet transmit time.
Non-persistent HTTP
Base page needs its own connection: (T1+T2). Each of the 4 images needs a brand-new connection: 4×(T1+T3).
Total = T1+T2+4(T1+T3) = 5T1 + T2 + 4T3
Persistent HTTP
Only ONE connection is opened for everything: T1 (once) + T2 (base page) + 4×T3 (images, reusing the same connection).
Total = T1 + T2 + 4T3
Non-persistent = 5T1+T2+4T3  |  Persistent = T1+T2+4T3 The difference is exactly 4T1 — the connection-setup time saved by NOT re-opening TCP for each of the 4 images. This "difference = (n−1)×T1" pattern is a fast sanity check for any symbolic HTTP question.

2.4Common Pitfalls — HTTP Math

⚠ Pitfall 1 — Forgetting the base HTML file itself
"A page references 8 objects" often means 9 total fetches (base HTML + 8 objects), not 8. Read carefully whether the stated size/count already includes the base file.
⚠ Pitfall 2 — Reusing RTT for both handshake and request/response
Unless two separate RTT values are given, the SAME RTT number is used for the TCP handshake round trip AND every HTTP request/response round trip — don't invent a second, different value.
⚠ Pitfall 3 — Non-persistent ≠ automatically sequential
If the question says "n parallel TCP connections," you must use formula ② (round-based), not formula ①. Rounds = ⌈objects ÷ parallel connections⌉.
⚠ Pitfall 4 — Persistent "no pipelining" still pays 1 RTT per object
A common mistake is assuming persistent HTTP means "no extra RTT at all." It still needs 1RTT+FTT per object (just skips the second RTT for a fresh TCP handshake) — only pipelining collapses multiple objects into a single shared RTT.
⚠ Pitfall 5 — bits vs bytes in bandwidth division
Object sizes are usually given in Bytes/Kbytes/MB, but link speed is in bits/sec (Mbps/Gbps/Kbps). Always convert size to bits (×8) before dividing by the bandwidth in bps.

2.5Full-Marks Answer Checklist — HTTP Math Questions

  • Count objects correctly — check if the base HTML file is separate from or included in the stated "n objects."
  • Compute every FTT explicitly (show the bits÷bps division) before plugging into any formula.
  • Write the general formula symbolically first (e.g. "n×(2RTT+FTT)"), then substitute numbers — partial marks are given for the correct formula even with an arithmetic slip.
  • Draw the simple client–server ladder diagram with RTT arrows whenever "sequence diagram" or "illustrate" is requested.
  • State units clearly on your final answer (ms vs s) — a numerically correct but mislabeled answer often loses a mark.
  • If asked to compare non-persistent vs persistent, always add one line of interpretation (e.g. "persistent saves n RTTs of connection setup").
