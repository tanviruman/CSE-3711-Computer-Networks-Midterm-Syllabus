1.1 What Is the Internet? What Is a Protocol?

Two views of the Internet

1. "Nuts and bolts" view: the Internet is billions of connected computing devices called hosts / end systems, running network apps at the network's "edge," connected by communication links (fiber, copper, radio, satellite — each with a transmission rate / bandwidth) and packet switches (routers and switches) that forward packets (chunks of data). It is a "network of networks" — mobile networks, home networks, enterprise networks, ISPs (local/regional and national/global), datacenter networks, and content-provider networks all interconnect. All of this activity is governed by protocols (HTTP, TCP, IP, WiFi, 4G/5G, Ethernet, …), standardized as RFCs (Request for Comments) by the IETF (Internet Engineering Task Force).

2. "Services" view: the Internet is infrastructure that provides services to applications (Web, streaming video, email, e-commerce, social media, …) — it gives apps a programming interface (sockets) to "connect" to the network, analogous to how the postal service offers different service options to its users.

What's a protocol?

A protocol defines the format and order of messages exchanged between two or more communicating entities, as well as the actions taken on message transmission and/or receipt. Just like a human protocol ("Hi" → "Hi" → "Got the time?" → "2:00") has rules for what to say and when, a computer network protocol (e.g., a TCP connection request/reply followed by a GET request and file response) governs exactly the same thing — format, order, and reaction to events.

Exam angle

"What is a protocol?" and "give an example of a human protocol vs network protocol" are classic short-answer questions. Always mention all three parts of the definition: (1) format/syntax of messages, (2) order of messages sent/received, (3) actions taken on transmission or receipt of a message or other event.

1.2 Network Edge, Access Networks & Physical Media

Network edge vs. network core

From slides: "A closer look at Internet structure"
  • Network edge: hosts — clients and servers (servers often live in data centers).
  • Access networks & physical media: the wired/wireless links that connect end systems to the first router ("edge router") on a path to any other end system.
  • Network core: the mesh of interconnected routers — the "network of networks."

  • Twisted pair (TP): two insulated copper wires. Cat 5 → 100 Mbps/1 Gbps Ethernet; Cat 6 → 10 Gbps Ethernet.
  • Coaxial cable: two concentric copper conductors, bidirectional; broadband = multiple frequency channels on one cable, 100s of Mbps per channel.
  • Fiber optic cable: glass fiber carrying light pulses (each pulse = one bit). High-speed point-to-point (10s–100s of Gbps), low error rate, immune to electromagnetic noise.
Unguided media — signal propagates freely (radio)
  • Wireless LAN (WiFi): 10–100s of Mbps, tens of meters.
  • Wide-area cellular (4G/5G): ~10s of Mbps over ~10 km.
  • Bluetooth: cable replacement, short range, limited rate.
  • Terrestrial microwave: point-to-point, ~45 Mbps channels.
  • Satellite: up to <100 Mbps downlink; ~270 ms end-to-end delay for geostationary satellites.

Host sending function & transmission delay

A host breaks an application message into packets of length L bits and transmits into the access network at transmission (link) rate R — also called link capacity or bandwidth.

Packet transmission delay
$$ d_{trans} = \dfrac{L \text{ (bits)}}{R \text{ (bits/sec)}} $$

1.3 The Network Core: Switching, Forwarding & Routing

Forwarding vs. Routing (a favorite short-answer trap)

Two key network-core functions
  • Forwarding (a.k.a. "switching"): the local action of moving an arriving packet from a router's input link to the appropriate output link, using the router's local forwarding table (destination address → output link).
  • Routing: the global action of determining the source-destination paths taken by packets, carried out by routing algorithms — the results of which fill in each router's local forwarding table.
⚠ Common pitfall

Students swap these two. Memory trick: Forwarding = local ("which door do I push this packet out of, right now?"). Routing = global ("what's the best path across the whole network?"). Routing algorithms build the forwarding table; forwarding just looks it up.

Packet switching: store-and-forward, queueing, loss

Store-and-forward: the entire packet must arrive at a router before it can be transmitted onward on the next link. Packet transmission delay = time to "push" (transmit) an L-bit packet into a link of rate R bps, i.e. L/R.

Queueing: occurs when work arrives at a link faster than it can be serviced — packets wait in a buffer for their turn. If the arrival rate exceeds the link's transmission rate for a period of time, the queue grows, and if the buffer fills up, arriving packets are dropped (lost).

Circuit switching: FDM & TDM

In circuit switching, end-to-end resources are allocated and reserved for a "call" between source and destination before data flows — dedicated, no sharing, guaranteed (circuit-like) performance. A circuit segment sits idle if the call isn't using it (no statistical sharing). Commonly used in traditional telephone networks.

FDM (Frequency Division Multiplexing): the link's frequency spectrum is divided into narrow bands; each call gets its own band and can transmit at the max rate of that narrow band, continuously.

TDM (Time Division Multiplexing): time is divided into slots (grouped into frames); each call is allocated periodic time slot(s) and can transmit at the maximum rate of the (wider) link — but only during its own slot(s).

TDM effective per-user rate
$$ \text{Effective rate for a user} = \left(\frac{\text{slots owned by that user}}{\text{total slots in the frame}}\right) \times R_{link} $$
⚠ Common pitfall — TDM "slot fraction" trap (appears in CT01!)

Watch out when a problem says something like "TDM with 30 slots, but this user gets every 3rd slot." The total slot count (30) can be a distractor — what actually matters is the fraction of slots owned. "Every 3rd slot" means the user owns 1 out of every 3 slots, i.e., a 1/3 share of the link — regardless of whether the frame has 30, 60, or 300 slots in it. Effective rate = R × (1/3), not R/30. Always ask: "what fraction of the cycle is actually mine?"

Worked micro-example (Workbook Exercise 4 style)

"How long to send a 640,000-bit file over a circuit-switched network? All links 1.536 Mbps, TDM with 24 slots/sec, 500 ms to establish the circuit."

Step 1 — per-user rate
Here "24 slots/sec" directly IS the number of slot-cycles the user gets per second at the full link rate — this style means the effective circuit rate = 1.536 Mbps / 24 = 64,000 bps (this is the classic "one telephone channel" DS0 rate, by design).
Step 2 — transmission time
640,000 bits ÷ 64,000 bps = 10 seconds.
Step 3 — add setup time
10 s + 0.5 s = 10.5 seconds total.

Packet switching vs. circuit switching — the classic comparison

Example from slides

1 Gbps link, each user needs 100 Mbps when "active," active 10% of the time. Circuit switching supports exactly 10 users (1000/100). Packet switching, with statistical multiplexing, can support 35 users with probability of more than 10 being simultaneously active being under 0.0004 — i.e., packet switching can serve far more users with only a tiny risk of congestion, when the average load is comfortably below capacity.

Circuit switching — max users (M)
$$ M = \left\lfloor \frac{\text{Link capacity } C}{\text{Per-user reserved rate } R} \right\rfloor $$
Packet switching — probability more than M of N users active (Binomial)
$$ P(X > M) = 1 - \sum_{k=0}^{M} \binom{N}{k} p^{k} (1-p)^{N-k} \qquad X \sim \text{Binomial}(N, p) $$

N = total users, p = probability a given user is active, M = circuit-switching capacity found above.

Concept you must be able to argue both ways

Packet switching advantages: great for "bursty" data, resource sharing, simpler (no call setup). Disadvantage: excessive congestion possible — packet delay and loss from buffer overflow; needs protocols for reliable transfer and congestion control. Whether packet switching actually "wins" in a given numeric problem depends entirely on the computed probability — see the pitfalls list and the CT01 Q2(d) solved example for a case where the answer is NOT the textbook default.

Internet structure — "network of networks"

Hosts connect via access ISPs; access ISPs interconnect via regional ISPs, which connect to a small number of highly-connected Tier-1 ISPs (e.g., Level 3, Sprint, AT&T, NTT — national/international coverage). Content-provider networks (Google, Facebook/Meta) run their own private networks connecting their data centers to the Internet, often bypassing Tier-1/regional ISPs entirely for performance. Networks interconnect at IXPs (Internet Exchange Points).

1.4 Delay, Loss & Throughput — the biggest numerical topic

Four sources of packet (nodal) delay

From slides: "Packet delay: four sources"
  • dproc — nodal processing: check for bit errors, determine output link. Typically < microseconds.
  • dqueue — queueing delay: time waiting at the output link for transmission; depends on router congestion level.
  • dtrans — transmission delay: L/R (L = packet length in bits, R = link rate in bps).
  • dprop — propagation delay: d/s (d = physical link length, s = propagation speed, ≈ 2×108 m/s in most media).
Total nodal delay
$$ d_{nodal} = d_{proc} + d_{queue} + d_{trans} + d_{prop} $$
⚠ Common pitfall — transmission delay ≠ propagation delay

These are the two most-confused terms in the entire course. Transmission delay is about pushing bits into the link — it depends on packet size and link rate (L/R), and happens once per hop, at the sender/router. Propagation delay is about how long a bit takes to travel across the physical medium once it's on the wire — it depends only on distance and propagation speed (d/s), and does not depend on packet size or link rate at all. If a question only asks for propagation delay, any given file-size or bandwidth number is a distractor (see CT01 Q3).

Caravan analogy

Car ↔ bit; caravan ↔ packet; toll booth ↔ router/link. Transmission delay = time to push the entire caravan through one toll booth = (number of cars) × (service time per car). Propagation delay = time for one car to travel the distance between two toll booths at the given speed = distance / speed.

Classic twist: "how many cars are still waiting at the first booth when the first car reaches the second booth?" — compute (service time for the first car + propagation time) = time elapsed, then divide that elapsed time by the per-car service time to find how many cars have fully exited booth 1; the rest are still waiting.

Packet loss & throughput

Packet loss: the queue (buffer) preceding a link has finite capacity. A packet arriving to a full buffer is dropped ("lost"). It may be retransmitted by the previous node, the source end system, or not at all.

Throughput: the rate (bits/time unit) at which bits are transferred from sender to receiver. Instantaneous = rate at a point in time; average = rate over a longer period. If the path has links of rate Rs (server) and Rc (client), the bottleneck link constrains end-to-end throughput.

End-to-end throughput (single connection across k links)
$$ \text{Throughput} = \min(R_1, R_2, \dots, R_k) $$
Throughput when N connections fairly share a bottleneck backbone link R
$$ \text{Per-connection throughput} = \min\left(R_c,\ R_s,\ \frac{R}{N}\right) $$
✓ How to spot the bottleneck fast

Whatever the smallest number on the end-to-end path is (after dividing any shared backbone link by the number of connections sharing it), that's your throughput. Don't average the rates — take the minimum.

1.5 Protocol Layers, Service Models & Encapsulation

Why layering?

Air travel analogy (from slides)

Airline travel is organized in layers: ticketing → baggage → gates → runway → airplane routing — each layer implements a service via its own actions, relying on the layer below. Why layer? (1) Explicit structure allows identification of the relationship between a complex system's pieces — gives a reference model for discussion. (2) Modularization eases maintenance and updating: a change in one layer's implementation (e.g., a new gate procedure) is transparent to the rest of the system, as long as the layer's service interface to its neighbors doesn't change.

The layered Internet protocol stack (5 layers)

Application — HTTP, IMAP, SMTP, DNS
Transport — TCP, UDP
Network — IP, routing protocols
Link — Ethernet, 802.11 (WiFi), PPP
Physical — bits "on the wire"
  • Application: supports network applications.
  • Transport: process-to-process data transfer.
  • Network: routing of datagrams from source to destination.
  • Link: data transfer between neighboring network elements.
  • Physical: moving individual bits "on the wire."

Services, layering, and encapsulation — step by step

At the source: the application hands a message M to the transport layer. The transport-layer protocol encapsulates M with a transport header Ht → forms a segment [Ht|M]. The network layer encapsulates the segment with a network header Hn → forms a datagram [Hn|Ht|M]. The link layer encapsulates the datagram with a link header Hl → forms a frame [Hl|Hn|Ht|M]. This is transmitted bit-by-bit at the physical layer. At the destination, each layer strips (de-encapsulates) its own header on the way back up, delivering M to the receiving process. The slides use the Matryoshka (Russian nesting) dolls analogy for this: message ⊂ segment ⊂ datagram ⊂ frame.

Encapsulation, layer by layer (source side)
M— message (Application)
HtM— segment (Transport)
HnHtM— datagram (Network)
HlHnHtM— frame (Link)
Encapsulation: the end-to-end view (router in the middle)

A router only understands up to the network layer: it de-encapsulates an arriving frame up to the datagram [Hn|Ht|M], reads Hn to decide the output link, then re-encapsulates with a fresh link-layer header for the next hop, and re-transmits. A link-layer switch only understands up to the link layer: it de-encapsulates a frame just enough to read the link-layer header, then re-encapsulates and forwards — it never even looks at Hn. Only the two end hosts process all 5 layers.

OSI vs TCP/IP — similarities & differences (verbatim from slides)

Similarities: both have layers; both have application layers (though different services); both have comparable transport and network layers; both assume packet-switched (not circuit-switched) technology; networking professionals need to know both models.

Differences: TCP/IP combines OSI's presentation + session layers into its single application layer; TCP/IP combines OSI's data link + physical layers into one (network access) layer; TCP/IP appears simpler (fewer layers); TCP/IP's transport layer using UDP does not always guarantee reliable delivery the way OSI's transport layer does.

Questions like "among HTTP, TCP, UDP, IP, Ethernet — which are implemented in the router(s)?" trip people up because they forget TCP/UDP/HTTP are end-to-end (transport & application) protocols that only the two communicating hosts process. A router only ever touches IP (network) and Ethernet (link/physical, re-done per interface) — never TCP, UDP, or HTTP.

Why security matters

The Internet was not originally designed with security in mind — the original vision was "a group of mutually trusting users attached to a transparent network." Protocol designers have been playing "catch-up" ever since; security must now be considered at all layers.

Security goals (from the slides, in order presented)

GoalMeaning
ConfidentialityOnly the sender and intended receiver should "understand" the message contents. Sender encrypts, receiver decrypts.
AuthenticationSender and receiver want to confirm the identity of each other.
Message IntegritySender and receiver want to ensure the message is not altered (in transit or afterward) without detection.
Access & AvailabilityServices must be accessible and available to legitimate users.
Basic components of security — CIA
  • C — Confidentiality: protection of data from unauthorized disclosure.
  • I — Integrity: assurance that the data received is exactly as it was sent by an authorized entity.
  • A — Availability: the ability to access data whenever it's needed.

Extended version sometimes called "CIAAAN": also includes Authentication (verifies identity of a user/service), Authorization (determines access rights), and Non-repudiation (protection against a party later denying they sent/received a communication).

Alice, Bob & Trudy — the standard cast of network security

Bob and Alice want to communicate "securely." Trudy (the intruder) may intercept, delete, or add messages on the channel between them. Real-life "Bobs and Alices" include: a web browser/server doing an on-line purchase, an on-line banking client/server, DNS servers, and BGP routers exchanging routing updates.

What can a "bad guy" do? (Attack types)

AttackOne-line definition (from slides)
EavesdroppingIntercept messages traveling on the network without the parties' knowledge.
Packet sniffingA passive receiver on a broadcast medium (shared Ethernet/WiFi) records a copy of every packet that flies by — a promiscuous network interface reads/records all passing packets, including passwords.
Impersonation / IP SpoofingFake (spoof) the source address in a packet — or any field — to appear as someone else; injecting a packet with a false source address.
Hijacking"Take over" an ongoing connection by removing the sender or receiver and inserting oneself in their place.
Denial of Service (DoS)Prevent a service from being used by legitimate users — e.g., by overwhelming the target's resources (server, bandwidth) with bogus traffic from many compromised hosts (a botnet): (1) select target, (2) break into hosts around the network, (3) send packets to target from the compromised hosts.

Lines of defense

  • Authentication: proving you are who you say you are (e.g., a SIM card provides hardware identity in cellular networks; the traditional Internet has no such hardware assist).
  • Confidentiality: via encryption.
  • Integrity checks: digital signatures prevent/detect tampering.
  • Access restrictions: password-protected VPNs.
  • Firewalls: specialized "middleboxes" that are off-by-default and filter incoming packets to restrict senders, receivers, and applications; also detect/react to DoS attacks.

3.1 Client-Server vs P2P, Processes & Sockets

Client-server architecture
  • Server: always-on host, permanent IP address, often in data centers for scaling.
  • Clients: contact/communicate with the server; may be intermittently connected; may have dynamic IP addresses; clients do not communicate directly with each other.
  • Examples: HTTP, IMAP, FTP.
Peer-to-peer (P2P) architecture
  • No always-on server; arbitrary end systems directly communicate.
  • Peers request service from other peers and provide service in return — self-scalable (new peers bring new capacity AND new demand).
  • Peers are intermittently connected and change IP addresses → complex management.
  • Example: P2P file sharing.

Processes, sockets & addressing

A process = a program running within a host. Processes on the same host communicate via inter-process communication (defined by the OS). Processes on different hosts communicate by exchanging messages. The client process initiates communication; the server process waits to be contacted. (Note: P2P apps have both client and server processes in each peer.)

Socket: the process sends/receives messages to/from its socket — a socket is like a "door": the sending process shoves a message out the door, relying on the transport infrastructure on the other side of the door to deliver it to the socket at the receiving process. The socket interface is controlled by the OS below and the application developer above.

Addressing processes — why IP address alone isn't enough

A host has one unique 32-bit IP address, but many processes can run on that host simultaneously — so IP address alone can't identify a specific process. The identifier must include both the IP address AND the port number associated with the process. Example: HTTP server → port 80; mail server → port 25. To send an HTTP message to gaia.cs.umass.edu, you need IP 128.119.245.12 and port 80.

What an application-layer protocol defines (4 things)

  1. Types of messages exchanged — e.g., request, response.
  2. Message syntax — what fields are in messages and how fields are delineated.
  3. Message semantics — the meaning of the information in the fields.
  4. Rules for when and how processes send & respond to messages.

Open protocols (defined in RFCs, e.g. HTTP, SMTP) allow interoperability; proprietary protocols (e.g., Skype) do not.

⚠ Common pitfall

"Why is there a UDP at all, if it's unreliable?" — Because some apps (streaming, VoIP, DNS) prioritize speed and low overhead over reliability; they don't need retransmission, and TCP's reliability/congestion-control machinery adds delay these apps can't afford. Always be ready to justify UDP's existence this way rather than just calling it "the unreliable one."

3.2 The Web and HTTP

Web page basics

A web page consists of objects (HTML file, JPEG image, Java applet, audio file, …), each potentially stored on a different server. A page = one base HTML file that includes several referenced objects, each addressable by a URL: e.g. www.someschool.edu/someDept/pic.gif (hostname + path name).

HTTP = HyperText Transfer Protocol, the Web's application-layer protocol, client/server model: the client (browser) requests/receives/displays objects; the server sends objects in response. HTTP uses TCP: the client initiates a TCP connection (socket) to the server on port 80; the server accepts; HTTP messages are exchanged; the TCP connection is closed. HTTP is stateless — the server keeps no memory of past client requests.

Non-persistent vs. persistent HTTP

Non-persistent HTTP

TCP connection opened → at most one object sent over it → connection closed. Downloading multiple objects requires multiple connections (repeat steps 1–5 for each object).

Persistent HTTP (HTTP/1.1)

TCP connection opened once → multiple objects can be sent over the same connection → connection closed only at the end. Server leaves the connection open after responding; client sends new requests as soon as it discovers a referenced object.

Persistent HTTP — why it's faster

Non-persistent HTTP issues: needs 2 RTTs per object, plus OS overhead for every new TCP connection (browsers historically worked around this by opening several parallel connections). Persistent HTTP removes the repeated connection-setup RTT — as little as one RTT total for all referenced objects when pipelining is used, cutting response time roughly in half or more.

HTTP request message

The user configures their browser to point to a Web cache. Goal: satisfy the client's request without involving the origin server whenever possible.

A Web cache acts as both a server (to the original requesting client) and a client (to the origin server). Typically installed by an ISP (university, company, residential ISP).

3.4 Electronic Mail: SMTP & Mail Access Protocols

Three major components
  • User agents ("mail readers") — composing, editing, reading messages, e.g. Outlook, iPhone mail client.
  • Mail servers — hold the user's mailbox (incoming messages) and an outgoing message queue.
  • SMTP (Simple Mail Transfer Protocol) — used between mail servers to send email.
SMTP (RFC 5321) — key facts
  • Uses TCP to reliably transfer a message from the client (the sending mail server, which initiates the connection) to the server, on port 25.
  • Direct transfer: sending server acts like a client directly to the receiving server.
  • Three phases: handshaking (greeting), transfer of messages, closure.
  • Command/response interaction, like HTTP: commands are ASCII text, responses are a status code + phrase.
  • Messages must be in 7-bit ASCII.
  • Uses persistent connections; uses CRLF.CRLF to mark end of message.

  4. The SMTP client sends Alice's message over that TCP connection.

Mail access protocols — retrieving mail from the server

Never say "SMTP is used to retrieve mail" — SMTP only ever pushes forward, never retrieves.

3.5 DNS — Domain Name System

People are identified by SSN, name, passport #. Internet hosts/routers are identified by a 32-bit IP address (used for addressing datagrams) and a hostname like cs.umass.edu (used by humans). DNS maps between the two: a distributed database implemented as a hierarchy of many name servers, and an application-layer protocol that lets hosts and name servers communicate to resolve names. DNS is a core Internet function, but it is implemented at the application layer — complexity pushed to the network's edge.

Why not centralize DNS? (exact reasons)

  • Single point of failure — the whole Internet's naming breaks if it goes down.
  • Traffic volume — a single server can't handle the query load (Comcast alone handles ~600 billion DNS queries/day).
  • Distant centralized database — bad performance for users far away.
  • Maintenance — a single database for the whole Internet is unmanageable.

DNS services: hostname → IP address translation; host aliasing (canonical/alias names); mail server aliasing; load distribution (many IPs can map to one replicated web server's name).

DNS hierarchy — four kinds of servers

Iterated vs. Recursive DNS queries

Iterated query

Each contacted server replies with the name of another server to try next — "I don't know this name, but ask this server." The querier keeps contacting each subsequent server itself. This is the standard mode used between the local DNS server and the root/TLD/authoritative servers (they refuse to do the extra work of full recursion for every query).

Recursive query

Puts the burden of full name resolution on the contacted name server — it does all the subsequent querying itself and returns only the final answer. Creates heavy load at upper levels of the hierarchy if used everywhere, which is why root/TLD servers generally don't support it.

⚠ Common pitfall — "who contacts whom" & what gets cached

In the iterative model, the Local DNS server does all the work — it personally contacts Root, then TLD, then Authoritative, and caches every mapping it learns along the way (NS records and A records for each zone it passed through). The requesting host only ever talks to its Local DNS server once, and caches only the final answer. If a question instead says the resolution is fully recursive at the root (root delegates all the further querying itself), then even the Local DNS server sees and caches only the final answer — it never learns the intermediate NS/A records. This distinction is worth real marks in the Mid Term DNS questions — see Mid Summer25 Q3(c) and Mid Fall25 Q3(a).

Caching & updating DNS records

Once any name server learns a mapping, it caches it. Cache entries time out (disappear) after a TTL (time to live). TLD server addresses are typically cached at local name servers, so root servers aren't visited often. Cached entries may be out of date (best-effort translation) — if a host changes its IP, this may not be known Internet-wide until all TTLs expire.

3.6 P2P Applications & BitTorrent

P2P recap: no always-on server; peers directly communicate; self-scalable; intermittently connected with changing IPs; complex management. Examples: file sharing (BitTorrent), streaming (KanKan), VoIP (Skype).

File distribution time: Client-Server vs P2P

Notation: F = file size, us = server upload capacity, ui = peer i's upload capacity, di = peer i's download capacity, N = number of peers.

Client-Server distribution time
$$ D_{c\text{-}s} \geq \max\left\{\frac{NF}{u_s},\ \frac{F}{d_{min}}\right\} $$

Server must sequentially upload N copies (NF/us) — increases linearly with N; each client must also download its own copy (F/dmin).

P2P distribution time
$$ D_{P2P} \geq \max\left\{\frac{F}{u_s},\ \frac{F}{d_{min}},\ \frac{NF}{u_s + \sum u_i}\right\} $$

The server uploads only ONE copy; clients collectively must download NF bits, but total upload capacity now includes the server plus every peer — so capacity grows as peers join, giving P2P a huge scalability edge as N grows.

✓ Key exam takeaway

In Client-Server, distribution time grows linearly with N because only the server uploads. In P2P, aggregate upload capacity grows along with N (every new peer adds both demand AND supply) — this is exactly what "self-scalability" means, and it's why P2P dramatically outperforms client-server for popular, large files.

BitTorrent — mechanics (exact terms from slides)

  • File divided into 256 Kb chunks.
  • Torrent: the group of peers exchanging chunks of one file.
  • Tracker: tracks which peers are participating in a torrent.
  • A joining peer: has no chunks initially; registers with the tracker to get a list of peers; connects to a subset of peers ("neighbors"); while downloading, it also uploads chunks to others; churn — peers may come and go; once a peer has the whole file it may (selfishly) leave or (altruistically) remain a "seed."

Requesting & sending chunks — "rarest first" and "tit-for-tat"

MechanismRule
Requesting chunksPeriodically ask each neighbor what chunks they have; request the missing chunks, rarest first (so rare chunks spread through the swarm quickly).
Sending chunks (tit-for-tat)Send chunks to the 4 peers currently sending you data at the highest rate — others are "choked" (don't receive from you). Re-evaluate the top 4 every 10 seconds.
Optimistic unchokeEvery 30 seconds, randomly pick another peer and start sending to them anyway — this "optimistically unchoked" peer may prove to be a good trading partner and join the top 4.
Tit-for-tat in action

(1) Alice optimistically unchokes Bob. (2) Alice becomes one of Bob's top-4 providers; Bob reciprocates. (3) Bob becomes one of Alice's top-4 providers. Lesson: a higher upload rate helps you find better trading partners and get the file faster — this is BitTorrent's built-in incentive against free-riding.

B Common Pitfalls & Question Analysis (Master List)

Every entry below is tied to a real pattern found in your CT01, CT02, or Mid Term papers. Read this before attempting Part C.

Pitfall Category 1 — Distractor Numbers (data you don't actually need)

⚠ Pitfall 1.1 — Extra data given for a delay you're not asked to find

Where it appears: CT01 Q3 gives a 30 Mb file size but only asks for propagation delay (which needs only distance + speed). Rule: before touching any numbers, re-read exactly which delay/quantity is being asked. Transmission delay needs (L, R). Propagation delay needs (d, s). If a number in the problem doesn't map to a variable in the formula for what's actually asked, it's a distractor — don't force it in.

⚠ Pitfall 1.2 — Total slot count vs. actual slot fraction owned (TDM)

Where it appears: CT01 Q1 ("TDM with 30 slots... every 3rd slot"). Rule: the fraction of the frame a specific user actually owns is what sets their effective rate, not the frame's total slot count. Re-derive the fraction from the wording, don't assume 1/(total slots).

⚠ Pitfall 1.3 — "% active time" is irrelevant for circuit switching capacity

Where it appears: Mid Summer25 Q1(c). Rule: circuit switching reserves fixed dedicated bandwidth whether or not the user is actively transmitting. The "active X% of the time" figure only matters for the packet switching / probability part of a question — never for computing circuit-switching capacity (that's purely link capacity ÷ per-user reserved rate).

Pitfall Category 2 — Which Layer / Which Device Traps

⚠ Pitfall 2.1 — "Which protocols run on the router?"

Where it appears: CT02 Q1(c), Mid Summer25 Q1(a)(II). Rule: routers only process Network layer and below (IP + Ethernet/link + physical). TCP, UDP, HTTP, SMTP are end-to-end (transport/application) protocols — only the two communicating hosts implement them. A link-layer switch goes one level lower still — it never even reads the IP header, only Ethernet/MAC.

⚠ Pitfall 2.2 — MAC address changes every hop; IP address and port do NOT

Where it appears: CT02 Q1(d) packet header table. Rule: Source/Destination IP and Port are end-to-end — they describe the ultimate sender and receiver, and stay fixed across the entire path. Source/Destination MAC describes only the current physical hop and is rewritten by every router the packet passes through (the router puts its own MAC as the new source, and the next hop's MAC as the new destination).

⚠ Pitfall 2.3 — SMTP is a "push," never a "pull"

Where it appears: Mid Summer25 Q2(a), email-path questions in every Mid. Rule: never write that SMTP is used to "retrieve" or "download" mail — SMTP only ever pushes a message forward (sender's server → receiver's server). Retrieval to the end user is always IMAP, POP3, or a webmail HTTP interface.

Pitfall Category 3 — Unit & Conversion Traps

⚠ Pitfall 3.1 — Mixing bits and bytes

File/message sizes are almost always given in bytes or KB/MB, but link rates are in bits per second (bps/Kbps/Mbps/Gbps). Always convert size → bits (× 8) before dividing by a rate in bps. This single mistake accounts for most numerical errors across CT02 Q1(b), Mid Fall25 Q1(d), Mid Spring26 Q1(c), and every HTTP timing question.

⚠ Pitfall 3.2 — Propagation delay is almost always negligible next to transmission delay for short links — but don't just drop it

Where it appears: Mid Summer25 Q1(b), Mid Spring26 Q1(d). Rule: for very short distances (meters to a few km) with reasonable propagation speeds (~2×10⁸ m/s), propagation delay ends up in the microsecond range while transmission delay can be in the millisecond-to-second range. Still compute and show it for full marks — just note in your answer that it's negligible compared to transmission delay, don't silently omit it.

⚠ Pitfall 3.3 — Rounding number of segments/frames UP, always

Where it appears: CT02 Q1(b), Mid Fall25 Q1(d), Mid Spring26 Q1(c). Rule: when dividing total data by max payload per segment, the number of segments must always be rounded up (ceiling) — you cannot send a fractional segment, so any remainder needs one more full segment, even if it only carries a few leftover bytes.

Pitfall Category 4 — HTTP Timing Formula Mix-ups

⚠ Pitfall 4.1 — Forgetting the base HTML file is a separate connection/RTT too

Where it appears: CT02 Q2, Mid Fall25 Q2(b), Mid Spring26 Q2(b). Rule: the base HTML page itself needs to be fetched (1 connection under non-persistent) before the browser even knows what embedded objects exist — always count it as one of your N objects, even if its own transmission time is ~0.

⚠ Pitfall 4.2 — Persistent "no pipelining" vs "with pipelining" give very different numbers

Rule: No pipelining = client waits for each response before sending the next request → (1+N)×RTT + ΣFTT. With pipelining = all remaining requests fired in one burst after the base page → 3RTT + ΣFTT(all). If the question is silent on pipelining, default to "no pipelining" (the more conservative baseline) but mention the pipelined variant if time allows — see Mid Spring26 Q2(b) analysis.

Pitfall Category 5 — DNS "Who Contacts Whom" & Caching

⚠ Pitfall 5.1 — Iterative vs recursive changes WHO caches WHAT

Where it appears: Mid Summer25 Q3(c), Mid Fall25 Q3(a-II). Rule: in an iterative resolution, the Local DNS server personally visits every level (root → TLD → authoritative) and therefore caches every intermediate NS/A record it sees along the way; the original requesting host only ever talks to the Local DNS once and only caches the final A record. If instead the resolution is recursive (say, the root itself does all the further querying), the Local DNS server only sees and caches the final answer too — it never learns the intermediate records.

⚠ Pitfall 5.2 — Root and TLD servers give REFERRALS, not answers

Rule: when writing out iterative DNS steps, don't say "root server tells local DNS the IP address." Root and TLD servers almost never hold the final A record — they hold NS records that refer the querier to the *next* server down the hierarchy. Only the authoritative server for the exact domain holds the actual A record.

Pitfall Category 6 — Circuit vs Packet Switching Probability Questions

⚠ Pitfall 6.1 — Assuming packet switching is "always better" without checking the actual probability

Where it appears: CT01 Q2(d) vs Mid Spring26 Q1(a-iii) — these two questions use the same formula but land on opposite conclusions! When the expected number of active users (N×p) is well below the circuit-switching capacity M, P(X>M) is tiny and packet switching clearly wins (Mid Spring26 case: P≈0.0000125). But when N×p is well above M, P(X>M) is close to 1 and packet switching will be congested almost constantly (CT01 case: P≈0.9978) — meaning the "packet switching is always better" textbook line does not automatically apply; you must reason from your own computed number, not from memory. See both fully worked out side-by-side in the CT01 and Mid Spring26 solutions in Part C.

Pitfall Category 7 — Security / CIA Definitions

⚠ Pitfall 7.1 — Confusing Confidentiality with Integrity

Where it appears: Mid Fall25 Q2(c). Rule: Confidentiality = nobody unauthorized can read the content (solved by encryption). Integrity = nobody can alter the content without it being detected (solved by hashing/digital signatures/MAC). A message can be confidential but still get corrupted undetected (no integrity); a message can be fully readable (no confidentiality) yet any tampering gets caught (integrity intact) — they are independent properties, and yes, you can have either without the other.

Q1 — TDM circuit-switching delay5 marks

Host A sends a 200,000-bit file to Host B over a circuit-switched network. All links are 60 Mbps; each link uses TDM with 30 slots (one slot per user), where this user gets every 3rd slot, and N seconds are needed to establish the end-to-end circuit (N = last two digits of your student ID). Find the total delay.

Given
L = 200,000 bits · R = 60 Mbps · slot pattern = every 3rd slot · setup = N seconds
Step 1 — Find this user's effective rate
"Every 3rd slot" means the user owns 1 out of every 3 slots in the frame — a 1/3 share of the link, regardless of the 30-slot detail. Effective rate = 60 Mbps × (1/3) = 20 Mbps.
Step 2 — Transmission delay
$d_{trans} = \dfrac{200{,}000 \text{ bits}}{20\times10^6 \text{ bps}} = 0.01\text{ s} = 10\text{ ms}$
Step 3 — Add circuit setup time
Total delay = N (setup, in seconds) + 0.01 s.
AnswerTotal delay = (N + 0.01) seconds = N seconds and 10 ms. (Plug in your own N = last 2 digits of your ID — e.g., ID ending in 47 → total delay = 47.01 s.)
Question analysis & common mistakes

This question tests whether you can find the correct fraction of link bandwidth owned by a single circuit inside a TDM scheme. The #1 mistake is dividing by 30 (the total slot count) instead of 3 (the "every 3rd slot" cycle) — giving a wrong rate of 2 Mbps instead of 20 Mbps, and a wrong delay of 100 ms instead of 10 ms. The #2 mistake is forgetting to add the N-second setup time at all, or adding it in the wrong units (some students write "N ms" instead of "N seconds" — the question explicitly says N seconds).

Q2 — Circuit vs packet switching + probability13 marks

C = 8 Mbps link, 50 total users, each needs R = 800 Kbps while transmitting, active 40% of the time.

Given

Step

AnswerM = 10 users

(b) Can circuit switching support N users? [2]

AnswerIf your N ≤ 10 → Yes. If your N > 10 → No (true for the large majority of IDs, since N ranges 0–99 but capacity is fixed at only 10).

(c) Probability that more than M users are transmitting (packet switching) [5]

Step 1 — Model
Each of the 50 users is active independently with probability p = 0.4. Let X = number of simultaneously active users. X ~ Binomial(n=50, p=0.4). We want P(X > 10).
$$ P(X>10) = 1-\sum_{k=0}^{10}\binom{50}{k}(0.4)^k(0.6)^{50-k} $$
Step 2 — Evaluate
Computing the cumulative sum for k = 0 to 10 gives P(X≤10) ≈ 0.0022, so:
AnswerP(X > 10) ≈ 0.9978 (about 99.78%)

(d) Which is better — circuit or packet switching? [3]

Reasoning
The expected number of simultaneously active users is N×p = 50×0.4 = 20 — already double the circuit-switching capacity (M=10). That's why part (c)'s probability came out so high (≈99.78%): packet switching will experience congestion/queueing almost all the time in this specific scenario, not just occasionally.
AnswerEven so, packet switching is still the better choice here: circuit switching can only ever admit 10 of the 50 users (the other 40 get zero service, permanently blocked), while packet switching lets all 50 users attempt to send — yes, with frequent queueing delay — but nobody is outright denied access. Packet switching trades guaranteed performance for universal access via resource sharing, which is the core justification for packet switching in the first place.

Given RRs: Aroot: {net, admin.university.net, NS} and {admin.university.net, 111.5.6.30, A}. Acom: {university.net, ns1.university.net, NS} and {ns1.university.net, 203.0.113.2, A}. Auniversity.net: {www→203.0.113.10, A}, {ftp→203.0.113.15, A}, {mail→203.0.113.20, A}.

II. Cached mappings at Local DNS L and Host C [3]

If the resolution is done ITERATIVELY (L contacts each server itself) L caches all 5 records it personally learned: (net → admin.university.net, NS), (admin.university.net → 111.5.6.30, A), (university.net → ns1.university.net, NS), (ns1.university.net → 203.0.113.2, A), (www.university.net → 203.0.113.10, A).

Question analysis & common mistakes

Students often assume Host C also caches all 5 intermediate records — it does not, regardless of whether L used iterative or recursive querying, because C's own interaction with L is always a single request/single response. Only L's cache contents differ between the iterative and recursive cases.

Q3(b) — Iterated DNS query for www.cisco.com + record types5 marks

I. Step-by-step iterated resolution [3]

  1. Host cse.uiu.ac.bd sends a DNS query for www.cisco.com to local DNS server dns.uiu.ac.bd.
  2. dns.uiu.ac.bd (no cache) sends an iterative query to a Root server.
  3. Root replies with a referral to the .com TLD server.
  4. dns.uiu.ac.bd sends an iterative query to the .com TLD server.
  5. .com TLD replies with a referral to cisco.com's authoritative server.
  6. dns.uiu.ac.bd sends an iterative query to cisco.com's authoritative server.
  7. Authoritative server returns the actual A record (IP) for www.cisco.com.
  8. dns.uiu.ac.bd returns the IP to the host (and caches it).
  9. The Safari browser now opens a TCP connection to that IP (port 80/443) and sends the HTTP GET for /index.html.

II. Function of A, MX, CNAME, NS records [2]

RecordFunction
AMaps a hostname → its IPv4 address.
MXMaps a domain → the hostname of its mail server.
CNAMEMaps an alias hostname → its canonical (real) hostname.
NSMaps a domain (zone) → the hostname of the authoritative name server for that zone.
Question analysis & common mistakes

Don't collapse steps 3–7 into "root tells the browser the IP" — every intermediate hop in an iterated query returns a referral, not the final answer; only the last (authoritative) server returns the A record. Also, don't confuse the HTTP request (step 9) with DNS resolution — DNS must fully complete before any HTTP request can be sent, since HTTP needs a destination IP address to open its TCP connection.

Q1(a) — Circuit vs packet switching + binomial probability5 marks

N users on a 0.5 Gbps switch link. Each user needs 50 Mbps, active 20% of the time.

Given
C = 0.5 Gbps = 500 Mbps · per-user rate = 50 Mbps · p = 0.2

i. Max users, circuit switching [1]

Step
M = 500/50 = 10
Answer10 users

ii. Packet switching, 15 users: P(11 or more active) [2]

Model
X ~ Binomial(n=15, p=0.2). Want P(X≥11) = 1 − P(X≤10).
$$ P(X\geq11) = 1-\sum_{k=0}^{10}\binom{15}{k}(0.2)^k(0.8)^{15-k} $$
AnswerP(X≥11) ≈ 0.0000125 (≈0.00125%) — vanishingly small.

iii. Compare circuit vs packet switching here [2]

AnswerExpected active users = 15×0.2 = 3, far below the circuit-switching capacity of 10 — so it's essentially impossible (~0.00125%) for demand to ever exceed capacity. Packet switching wins decisively here: it serves all 15 users (50% more than circuit switching's hard cap of 10) with negligible risk of congestion, while circuit switching would flatly block 5 of the 15 users even though they'd almost never actually need simultaneous service. Circuit switching's only advantage remains guaranteed, dedicated performance for its admitted users — useful for real-time/latency-critical traffic, but wasteful of capacity here.
Question analysis & common mistakes

Compare this directly to CT01 Q2, which uses the exact same formula but where expected active users (20) is double the circuit-switching capacity (10) — giving a probability of ~99.78% instead of ~0.00125%. Don't memorize "packet switching always wins" as a blind rule — you must actually compute N×p and compare it to M before concluding which one wins. This pair of questions is deliberately designed to test that you understand why, not just recite the textbook conclusion.

Q1(b) — Layered architecture + encapsulation/de-encapsulation5 marks

Host A —(R1,D1)— Router 1 —(R2,D2)— Host B.

i. How layering simplifies network operations [2]

Answer Modularity: each layer can be designed, implemented, and modified independently, as long as its service interface to neighboring layers stays the same.
Interoperability: layers built by different vendors can work together (e.g., any Ethernet card works with any IP stack).
Easier troubleshooting/maintenance: problems can be isolated to a specific layer rather than debugging the whole system at once.
Reusability: the same lower-layer service (e.g., IP) can support many different upper-layer applications.

ii. Encapsulation/de-encapsulation as M travels A → Router1 → B [3]

At Host A (full encapsulation, all 5 layers)
MApp
HtMTransport
HnHtMNetwork
HlHnHtMLink → sent on R1
At Router 1

De-encapsulates only up to the network layer: strips Hl, examines Hn (IP header) to pick the output link (toward B via R2), then re-encapsulates with a new link header Hl′ suited to link R2, and transmits. Transport and application layers are never touched at the router — Ht and M pass through completely unopened.

At Host B

Fully de-encapsulates: strips Hl′ → Hn → Ht, delivering M to the destination application process.

This is nearly identical in structure to Mid Summer25 Q1(a)(I) — the recurring trap is having the router "look inside" M or Ht, which never happens. Also, always explicitly mention the re-encapsulation step at the router (new Hl′ for the outgoing link) — just saying "the router strips the header" without adding a fresh one for the next hop loses marks.

Q1(c) — TCP segments + overhead %3 marks

2 MBytes application data. TCP=20B, IP=20B, DataLink=14B header+4B trailer, frame size 1500B excluding header/trailer.

Given
Data = 2,000,000 bytes · Frame payload capacity (excl. DL overhead) = 1500B
Step 1 — Max app data per segment
1500(network PDU) − 20(IP) − 20(TCP) = 1460 bytes.
Step 2 — Number of segments
⌈2,000,000/1460⌉ = 1370 segments (1369 full segments of 1460B + 1 final segment of 1260B, since 1369×1460=1,998,740 and remainder=1,260).
Step 3 — Overhead % (for a full-size segment)
Total transmitted per full segment = 1460(data)+20(TCP)+20(IP)+18(DL) = 1518B. Overhead = 58B. $$ \%\text{overhead} = \frac{58}{1518}\times100\% \approx 3.82\% $$
Answer1370 TCP segments needed; overhead ≈ 3.82% of transmitted bits for a full-size segment. (Note: the final, smaller 1260-byte segment has a slightly higher overhead ratio, ≈4.40%, since the fixed 58-byte overhead is spread over less data — worth a one-line mention for full marks.)

The phrase "frame size... excluding header and trailer" is the key detail — it means 1500B is already the max network-layer payload (you do NOT subtract 14+4 again). Compare this to Mid Fall25 Q1(d), which said 1518B including overhead — the two problems look similar but require different first steps. Always read whether the given frame size includes or excludes the data-link overhead before subtracting anything.

Q1(d) — End-to-end delay + bottleneck/throughput3 marks

Frame = 1500 bytes. R1=100 Mbps, R2=1 Gbps. D1=10m, D2=1km. Speed=1.5×10⁸ m/s. Router processing=1ms, no queueing.

Given
Frame=1500B=12,000 bits · R1=100Mbps, R2=1Gbps · D1=10m, D2=1000m · s=1.5×10⁸m/s · proc=1ms

i. Total end-to-end delay [2]

Transmission delays
$t_1 = 12{,}000/100\times10^6 = 0.12\text{ ms}$    $t_2 = 12{,}000/1\times10^9 = 0.012\text{ ms}$
Propagation delays
$p_1 = 10/(1.5\times10^8) ≈ 0.0000667\text{ ms}$    $p_2 = 1000/(1.5\times10^8) ≈ 0.00667\text{ ms}$
Sum (with 1 ms router processing, no queueing)

Q2(a) — What is a socket? Why port numbers?2 marks
Answer A socket is the interface (the "door") between an application process and the transport-layer protocol below it — the process sends/receives messages through its socket, and the OS/network takes care of getting bits to and from the socket at the other end.

Port numbers are needed because a single host's one IP address is shared by many processes running at once; the port number distinguishes which specific process on that host should receive an arriving segment. Example: a web server (port 80) and a mail server (port 25) can run simultaneously on the very same host/IP address — incoming segments are delivered to the correct one purely based on the destination port number in the segment header.
Q2(b) — Non-persistent vs Persistent HTTP, mixed object sizes3 marks

Webpage: 1 HTML (100 KB) + 2 CSS (150 KB each) + 8 images (2 MB each). Bandwidth = 1 Gbps. RTT (connection setup) = 0.2 ms.

Given
RTT=0.0002s · HTML=100KB, CSS=150KB×2, Image=2MB×8 · BW=1Gbps
Step 1 — FTT for each object type
HTML: 100,000B×8 = 800,000 bits ÷ 1×10⁹ = 0.8 ms
CSS: 150,000B×8 = 1,200,000 bits ÷ 1×10⁹ = 1.2 ms (each)
Image: 2,000,000B×8 = 16,000,000 bits ÷ 1×10⁹ = 16 ms (each)
Step 2 — Sum of all FTTs
0.8 + (2×1.2) + (8×16) = 0.8+2.4+128 = 131.2 ms
Step 3 — Non-persistent (11 total objects: 1+2+8)
$$ 11\times(2\times0.2) + 131.2 = 4.4+131.2 = 135.6\text{ ms} $$
Step 4 — Persistent, no pipelining
$$ (1+11)\times0.2 + 131.2 = 2.4+131.2 = 133.6\text{ ms} $$
AnswerNon-persistent HTTP: 135.6 ms. Persistent HTTP (no pipelining): 133.6 ms.

(If pipelining is assumed instead: 3RTT + ΣFTT = 0.6+131.2 = 131.8 ms — mention this alternative if your professor's phrasing implies pipelining.)

Question analysis & common mistakes

With very small RTT (0.2 ms) but large image files (16 ms FTT each), the RTT terms barely matter here — the bulk of the time comes from ΣFTT regardless of persistent/non-persistent. Don't get distracted trying to optimize the RTT count; the dominant cost is transmission time for the 8 large images. Also, remember 2 MB here should be read as 2,000,000 bytes (decimal) per this course's convention — using 2×1024×1024 would give a slightly different (larger) answer, so always double-check which convention a specific paper is using if the numbers don't come out clean.

Q2(c) — Slow distant server → web caching solution3 marks

Saadman's static galaxy-info site loads slowly because the server is very far away.

ProblemThe site's content must travel a very long physical distance for every single request, so both the connection-setup RTT and the transmission of each object suffer high propagation delay — this is a distance/latency problem, not a bandwidth problem.
Solution — Web CachingInstall/use a web cache (proxy server) located close to Saadman (e.g., within his ISP). His requests go to this nearby cache first: on a cache hit, the response comes back almost instantly (tiny local RTT) without ever contacting the distant origin server. Because the site is static and rarely changes, cached copies stay fresh for a long time — meaning a very high hit rate and consistently fast loading, plus reduced traffic on the long-haul link to the distant server.
Question analysis & common mistakes

Don't answer with "upgrade the bandwidth" — the problem describes a distant server (a latency/RTT issue), and bandwidth upgrades don't fix propagation delay. The "rarely changes" detail in the question is a deliberate hint pointing you toward caching (since caching works best for content with a long freshness window) — always use every detail the question gives you as a hint toward the intended concept.
